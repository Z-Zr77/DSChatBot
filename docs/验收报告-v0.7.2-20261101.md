## 2. 已确认的缺陷（按修复优先级）

### L2 · P1 · 只读会话仍能执行写文件命令【历史遗留】

位置：`pack/src/bridge.mjs:1244-1248`；执行入口 `3374-3399`，能力声明 `pack/src/tools.mjs:500-513`。

`toolCapsOk` 在处理 `exec` 能力时，只检查是否有活动会话以及全局 exec.mode 是否为 off，然后直接 continue；没有像 net/fs:write 一样调用 `grants.requireCap(..., 'exec', epoch)`。因此 caps 只有 fs:read 的会话也能进入 run_cmd。若审批策略是 never，会直接执行；ask 策略仍会把本应直接拒绝的操作送去审批。

**实际复现：**临时配置启用工作工具，exec.mode=workspace、approval=never；真实桥接创建 caps=[fs:read] 的会话。假模型请求执行工作区内的 `node probe-write.mjs`，成功生成内容为 `LOCAL_TEST_ONLY` 的测试文件。回读仍是 mode=read、caps=[fs:read]，日志含“策略=never，直接执行 run_cmd ok”。仅写本轮临时目录，未触碰用户文件。

建议：在执行/请求审批前检查 exec grant 与 epoch；审批策略不应代替能力授权。补测 read+ask、read+never 均不得启动进程或产生文件，write+exec 的正常审批仍可用。

归因：bridge.mjs 未在四个提交中修改；这是当前版本的历史权限漏洞，不归因于本批。

### F1 · P1 · 聊天窗首条任务没有发送，却提示成功【本批新增】

位置：`pack/src/workdialog.mjs:153-157`；对照 `pack/src/chatserver.mjs:315-328`、`pack/src/chatui.html:422`、`pack/src/ui.mjs:2085-2092`。

共享弹窗固定 POST `/api/chat/send`。这个路径只存在于控制台；聊天窗使用 `/api/send`，前者在聊天窗返回 404 `{ok:false}`。聊天窗 api 包装将失败转成返回对象，而弹窗既不检查 ok，也不检查错误字段，随后无条件提示“已经发给她了”。控制台收到业务失败 JSON 时也有同样的假成功提示。

**实际复现：**真实 chatserver + 本地桩桥接中，点击开始后 `/api/chat/send`=404，桥接 `/say` 收到 0 次，弹窗关闭并提示成功。对照 `/api/send`=200，桥接收到 1 次。另注入 `{ok:false,err:'TEST_BACKEND_UNAVAILABLE'}`，依旧提示成功。

建议：由各入口传入发送回调或正确路径，发送后检查 ok/err/error。失败时保留可重试的任务内容。分别覆盖 console/chat 两个入口的成功、HTTP 失败和业务失败。

归因：`96e37f4` 新增首任务自动发送。

### L1 · P2 · 保存“只读”档位后，新会话仍开成可写【历史遗留】

位置：`pack/src/workdialog.mjs:138-144`；对照 `pack/src/bridge.mjs:4508-4518`、`pack/src/chatui.html:809-812`。

后端保存 defaultMode，界面也承诺“下次进入用这档”，但弹窗启动请求固定携带 fs:read/fs:write/exec，并固定 confirmWrite=true。保存的 read/full 均不参与新会话授权。

**实际复现：**真实桥接 POST `/work/mode` 保存 read 后，提交弹窗实际生成的 caps，回读 mode=write，具有写入与命令权限。用户选择的限制被静默覆盖。

建议：提交时采用当前有效档位；不要仅在界面显示它。覆盖 read/write/full 的保存、停止、重新开始流程。

归因：基线 da3bf30 已有同类问题：旧代码读取不存在的 `input[name="wkMode"]:checked` 后默认 write。本批改成硬编码后仍然存在，不算本批新引入。

### F2 · P2 · “要联网”示例启动后必缺少联网能力【本批新增】

位置：`pack/src/workdialog.mjs:34-37`、`138-155`；对照 `pack/src/bridge.mjs:1236-1241`。

第三个例子承诺查询 Node 22 并写调研文件，点击开始即发送；会话固定授予 fs:read/fs:write/exec，没有 net，界面也没有在发送前完成权限选择。

**实际复现：**执行真实弹窗回调得到上述 caps，`grants.requireCap('net')` 拒绝；再用真实桥接与假模型返回 fetch_url，日志出现 `fetch_url caps-reject 这个会话没有开通「net」`，错误已回传给假模型。

建议：在发送前明确选择并确认所需权限，或仅展示当前权限能执行的例子；不要通过偷偷增加 net 来修复。修复 F1 后仍需单独修复此项。

归因：`96e37f4` 将联网例子放入自动发送流程。

### F4 · P2 · 原生框等待超过 90 秒，聊天窗提前降级并丢失结果【本批启用路径的问题】

位置：`pack/src/workdialog.mjs:106-114`；对照 `pack/src/chatserver.mjs:151-164,299-304`、`pack/src/bridge.mjs:4460-4466`。

聊天代理 upStrict 上限是 90 秒，桥接原生框请求上限是 120 秒。用户仍在原生框内浏览时，聊天代理就可提前失败；弹窗将失败一律作为降级依据，展开网页列表，之后原生框的选择/取消结果无法回填。Electron 没有随代理超时取消原生框的逻辑。

**实际复现：**未修改的 chatserver + 弹窗脚本，本地桩后端计划 95 秒返回 canceled。实测 90017 毫秒就展开列表，并请求目录 1 次。这个用例模拟等待中的原生框，没有实点 Windows 对话框；90 秒代理行为为真实执行，未缩短计时。

建议：统一整条选择框链路的等待/取消约定，区分“平台不支持”和“已打开但等待/失败”，避免两个选择器并存。测试立即取消、95 秒选择/取消、Electron 不存在与后端错误。

归因：`5f68164` 恢复调用既有原生路径后暴露。正常立即 canceled 分支顺序本身正确。

### F3 · P2 · 审批卡片显示错误的命令超时【本批新增】

位置：`pack/src/ui.mjs:3563-3565`；对照 `pack/src/tools.mjs:501-513`、`pack/src/exec.mjs:163`。

真实参数叫 timeoutSec，实际运行还会使用 work.exec.timeoutMs 并限制到 1–300 秒。新卡片却读取 x.timeoutMs/x.args.timeoutMs，缺值一律显示 60 秒，同时移除了原参数 JSON。用户失去核对真实超时的途径。

**实际复现：**用真实 UI 服务输出的 pollApprovals 渲染函数输入 `args.timeoutSec=5`，输出“超时 60 秒”，且不再展示 timeoutSec 原值。

建议：后端提供最终生效的 timeoutMs，前端换算秒；至少先正确识别 timeoutSec 并保留必要参数。补测显式 5/300 秒、自定义默认超时及上下限。

归因：`f120c8d` 修改 run_cmd 审批卡片。
